Home Lab Architecture

Build a playground you own. Isolation is the whole point — it is also what keeps your practice legal.

ISOLATE THE LAB

If it can reach a network you don't own, it isn't a lab.

Networking rules

  • Host-only — VMs see each other and the host, nothing else
  • NAT — outbound for updates only, no inbound exposure
  • Snapshots — clean state before and after every exercise
  • Own the images — deliberately vulnerable VMs built for testing
⚠Never point lab tools at machines, networks or accounts you do not own or have written permission to test.

HACKDOOR Technologies commissioned an authorised penetration test of its customer portal, support platform and internal web tier. Testing was performed under a signed scope and rules-of-engagement document, confined entirely to systems HACKDOOR owns and explicitly approved.

What we found

The dominant theme is authorization. The application reliably confirms who a user is, but inconsistently confirms what that user is permitted to reach. Combined with an injection flaw in the support platform and no protection against credential guessing, a single low-privileged account can be used to reach customer data at scale.

Two findings are rated Critical: cross-customer invoice access through broken access control, and database injection in ticket search. Both are reachable by any authenticated user and both expose data belonging to other customers.

The encouraging part

None of these issues are exotic. Eight of the ten are resolved by four durable engineering controls — server-side authorization checks, parameterized queries, adaptive password hashing, and centralized logging. We recommend treating those as one remediation programme rather than ten separate tickets, which is both faster and more durable than point fixes.

Recommended priority

0–14 DAYS

Enforce server-side ownership checks on every object-reference endpoint; parameterize the ticket search query; disable production debug endpoints and public storage-bucket listing.

15–45 DAYS

Enforce HTTPS everywhere including internal services; add login throttling, lockout and MFA for administrative roles; invalidate sessions on logout and credential change.

46–90 DAYS

Re-hash legacy password storage; introduce an SBOM with dependency scanning; centralize logging with alerting; require signature verification on the update mechanism.

Scope assurance

All testing remained inside the agreed scope. No denial-of-service, social-engineering or physical testing was performed. No customer data was extracted, retained or exfiltrated; evidence was limited to the minimum required to demonstrate each finding and was securely deleted at engagement close.

A01:2021 · BROKEN ACCESS CONTROL

Customers can read and modify other customers' invoices

CRITICALCVSS 9.1
customer.hackdoor.example → /api/v2/invoices/{id}Effort to fix: LOWStatus: OPEN

Description

The application checks that a user is signed in, but not that the requested record belongs to them. Changing the invoice identifier in the request returns a different customer's invoice. Authorization is being enforced in the user interface rather than on the server, so bypassing the interface bypasses the control entirely.

Impact

Any authenticated customer can read — and on some endpoints modify — billing records belonging to any other customer by stepping through identifiers. For HACKDOOR this means exposure of the entire client billing base, a likely breach-notification obligation, and direct commercial and reputational damage. It also fails the most basic requirement of customer data segregation.

Remediation

Enforce ownership on the server for every request: confirm the requesting user owns or is entitled to the specific object before returning it, and deny by default. Return 403 Forbidden rather than 404 so the control is explicit. Add automated tests that attempt cross-tenant access against every object-reference endpoint, and make those tests a release gate.

A02:2021 · CRYPTOGRAPHIC FAILURES

Passwords hashed with a fast algorithm; admin panel served over plain HTTP

HIGHCVSS 7.5
User database · password storageInternal admin panel · HTTP listenerEffort to fix: MEDIUM

Description

User passwords are stored using a fast, unsalted hash designed for speed rather than resistance to guessing. Separately, the internal administration panel is served over unencrypted HTTP inside the corporate network, so session cookies and credentials travel in the clear.

Impact

A single database leak — via backup exposure or any future injection flaw — yields credentials that can be recovered offline at high speed, and users routinely reuse passwords across services. The unencrypted admin panel allows anyone positioned on the internal network to capture administrative session tokens, converting a minor foothold into full administrative control.

Remediation

Re-hash all stored passwords with a memory-hard adaptive algorithm such as Argon2id (or bcrypt with a modern work factor), re-hashing transparently on next successful login and forcing a reset for accounts that remain dormant. Enforce HTTPS with HSTS on every service including internal ones, disable plain-HTTP listeners, and mark all session cookies Secure and HttpOnly.

A03:2021 · INJECTION

Ticket search builds database queries from user input

CRITICALCVSS 9.4
support.hackdoor.example → ticket search parameterEffort to fix: LOWStatus: OPEN

Description

The ticket search feature assembles its database query by concatenating the user's search text directly into the statement. Because the input is not separated from the query logic, crafted input changes what the query does and returns data the interface was never designed to display.

Impact

An attacker can read the full contents of the support database — every customer's conversations, internal notes and attachments — regardless of their own account. Depending on the database account's privileges, records may also be altered or destroyed. This is a complete confidentiality failure of the support platform and the fastest route to a reportable breach in this engagement.

Remediation

Use parameterized queries (prepared statements) for every database interaction so user input can never be interpreted as query logic — this removes the class of flaw rather than filtering individual characters. Run the application under a least-privilege database account, validate input against an allowlist of expected formats, and add automated injection test cases to the CI pipeline as a build gate.

A04:2021 · INSECURE DESIGN

Account recovery flow was designed without abuse protection

HIGHCVSS 7.2
Password reset · account recovery workflowEffort to fix: MEDIUMStatus: OPEN

Description

The account recovery workflow has no rate limiting, no lockout and no step-up verification. It assumes users behave correctly rather than defending against deliberate misuse. This is a gap in the design of the flow, not a coding mistake inside it — which is why it survived code review.

Impact

Recovery attempts can be repeated at scale across large numbers of accounts with no throttling and no alerting. Because the weakness is architectural, patching one endpoint will not close it; every new feature built on the same assumption inherits the flaw. Successful abuse leads directly to account takeover.

Remediation

Introduce threat modelling for business-critical flows before build, so abuse cases are designed against rather than discovered later. For this flow specifically: apply rate limiting and progressive lockout, issue single-use time-limited tokens, require step-up verification before sensitive changes, and alert on abnormal recovery volume per account and per source.

A05:2021 · SECURITY MISCONFIGURATION

Debug endpoints live in production; one storage bucket lists publicly

HIGHCVSS 7.8
Web server · cloud storage · framework debug modeEffort to fix: LOWStatus: OPEN

Description

Several services are running with insecure defaults. Verbose error pages disclose stack traces, framework versions and internal paths; a diagnostic endpoint intended for development is reachable in production; and one cloud storage bucket permits public listing of its contents.

Impact

Together these hand an attacker an accurate map of the technology stack, shortening the path from reconnaissance to a targeted exploit. The public bucket exposed internal documentation and backup archives — data that was assumed to be private purely because nobody had published a link to it.

Remediation

Define a hardened baseline configuration and enforce it through infrastructure-as-code so drift is detected automatically. Disable debug modes and verbose errors in every production environment, remove default and vendor accounts, apply least-privilege to cloud storage with deny-public defaults and bucket-level policy checks, and schedule recurring configuration audits with automated findings.

A06:2021 · VULNERABLE AND OUTDATED COMPONENTS

Third-party libraries and framework versions with known flaws

MEDIUMCVSS 6.3
Application dependencies · framework · container base imagesEffort to fix: MEDIUMStatus: OPEN

Description

The application depends on several third-party libraries and a framework release with publicly documented vulnerabilities, the oldest disclosed over two years ago. There is no inventory of third-party code and no defined cadence for applying updates.

Impact

Weaknesses that are already public can be exploited using published tooling, which lowers the skill required to attack HACKDOOR considerably. Even where a component is not directly reachable by users, it widens the attack surface, and the absence of an inventory means the organisation cannot answer the most basic supply-chain question during a customer security review.

Remediation

Maintain a software bill of materials (SBOM) covering application and container dependencies. Run automated dependency scanning in CI and block builds on critical findings, patch against a defined SLA by severity, remove unused dependencies, and pin and regularly rebuild container base images so known CVEs age out predictably.

A07:2021 · IDENTIFICATION AND AUTHENTICATION FAILURES

No login throttling, no MFA, and sessions survive logout

HIGHCVSS 8.1
Customer + admin login · session managementEffort to fix: MEDIUMStatus: OPEN

Description

The login endpoint applies no lockout or throttling, multi-factor authentication is not available for any role including administrators, and session tokens remain valid after logout and after a password change.

Impact

Password-guessing and credential-stuffing attacks can run continuously and invisibly. Because sessions are not invalidated, a token captured at any point stays usable indefinitely — even after the user logs out or changes their password believing they had ended the session. A single leaked token therefore becomes persistent access, and the absence of MFA removes the last barrier for administrative accounts.

Remediation

Add rate limiting and progressive account lockout on all authentication endpoints. Offer MFA to all users and require it for administrative and privileged roles. Invalidate every session on logout and on credential change, use short-lived sessions with secure server-side rotation, and alert on anomalous sign-in patterns such as impossible travel and high-volume failures.

A08:2021 · SOFTWARE AND DATA INTEGRITY FAILURES

Updates applied without signature verification; pipeline lacks integrity checks

MEDIUMCVSS 6.8
Automated update mechanism · CI/CD pipelineEffort to fix: MEDIUMStatus: OPEN

Description

The application applies updates retrieved from an external source without verifying a digital signature, and build artefacts move between pipeline stages without integrity verification at any hand-off.

Impact

If the update source or any stage of the pipeline is compromised, malicious code executes with the application's own privileges across the entire customer base. This is a supply-chain incident: hard to detect, hard to scope, and expensive to recover from, because the organisation has no way to prove which deployments were trustworthy.

Remediation

Require signed artefacts and verify signatures before installation, refusing anything unsigned or mismatched. Pin dependencies to known checksums, protect the pipeline with least-privilege credentials and mandatory review on changes to build definitions, and record all build and deploy events to an immutable, write-protected log so integrity can be demonstrated after the fact.

A09:2021 · SECURITY LOGGING AND MONITORING FAILURES

Security-relevant events are not logged and nothing is alerted on

MEDIUMCVSS 5.3
Application + authentication loggingEffort to fix: MEDIUMStatus: OPEN

Description

Failed logins, privilege changes and administrative actions are not recorded. The logs that do exist are stored only on the affected host, are not centrally reviewed, and generate no alerts.

Impact

Intrusion activity would go unnoticed for as long as it continued. Without an audit trail, HACKDOOR could not establish when an incident began, which accounts or data were touched, or what must be reported to customers and regulators — turning a contained issue into an unbounded one. It also removes the evidence needed to support any of the other findings in this report during incident response.

Remediation

Log all authentication events, privilege changes and sensitive actions with user identity, timestamp and source address. Ship logs to a central, write-protected store that the application itself cannot alter, define alert thresholds for failed-login volume and privileged-action anomalies, and rehearse the detection and response process through periodic tabletop exercises.

A10:2021 · SERVER-SIDE REQUEST FORGERY

Report preview fetches any URL the server can reach

HIGHCVSS 7.9
Reporting module → "fetch URL" preview featureEffort to fix: LOWStatus: OPEN

Description

The report preview feature accepts a user-supplied URL and retrieves it from the server. The server places no restriction on which addresses it will contact, so requests can be directed at internal-only services that are deliberately not exposed to the internet.

Impact

The application becomes a pivot into HACKDOOR's internal network. An attacker can reach administrative interfaces and cloud metadata services that trust internal callers, potentially disclosing temporary cloud credentials or reaching systems with no external attack surface at all. Trust boundaries drawn around "internal only" stop holding once the server will fetch on request.

Remediation

Use an allowlist of permitted destinations and protocols rather than a blocklist. Resolve hostnames and validate the resulting addresses before connecting, explicitly blocking private, loopback and link-local ranges; disable unnecessary URL schemes; apply a short timeout; and run the fetching component in an isolated, low-privilege network segment so a successful probe cannot reach sensitive services.
