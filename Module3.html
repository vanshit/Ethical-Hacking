How Does a Network Conversation Work?

Before any scanner makes sense, you need one clear mental model: a machine has an address, services listen on numbered doors, and a protocol is the language spoken through that door.

The eight words you must own

IP ADDRESS

The street address of a host on a network, e.g. victim-ip. It answers "which machine?"

MAC ADDRESS

The hardware address burned into a network card. It answers "which device on this local segment?" and works below IP.

PORT

A numbered door from 0–65535. It answers "which service on that machine?" Ports 0–1023 are well-known.

SERVICE

The program answering on that door — an SSH server, a web server, a database engine.

PROTOCOL

The agreed language and rules — HTTP, SSH, SMB, DNS. It answers "how do we talk?"

TCP

Connection-oriented transport: handshake first, then ordered, confirmed delivery. Used by SSH, HTTP, SMB.

UDP

Connectionless transport: fire and forget, no handshake. Used by DNS, DHCP, voice and video.

CLIENT / SERVER

The client starts the conversation; the server listens on a known port and responds.

Follow one request

Every remote service you will ever enumerate flows through this chain:

Client⟶ IP address⟶ Port⟶ Service⟶ Server
attacker-ip → victim-ip : 445 / TCP → SMB service

A port is not the service itself. A port is only a number. A service listens on that port using a protocol. Port 80 answering does not automatically mean "a web server" — it means something is listening and speaking HTTP. That is exactly why enumeration comes after discovery.

Ports worth recognising on sight

TCP/22SSH — encrypted remote shell
TCP/21FTP — file transfer (cleartext)
TCP/23Telnet — cleartext remote shell
TCP/25SMTP — mail transfer
TCP/80HTTP — web (unencrypted)
TCP/139NetBIOS session — legacy Windows networking
TCP/445SMB — Windows file / print sharing
TCP/3306MySQL — database

Meet Nmap

Nmap = Network Mapper. A free, open-source tool for discovering hosts and services on a network. Security professionals use it to understand a network before anyone attacks or defends it.

What Nmap can help you discover

Live hosts

Which machines on the network are up and responding.

Open ports

Which numbered doors accept connections.

Services

What kind of software answers on each open port.

Service versions

Which product and release — the key to researching known issues.

Operating-system clues

Hints about the platform, inferred from how it responds.

NSE-based information

Extra facts gathered by Nmap's scripting engine.

Why scan at all?

Scanning is not the goal. It is the first step of a repeatable analyst workflow:

Reading the output

Nmap's output is a sentence in four columns. Learn to read them left to right:

Meaning of Nmap output columns
ColumnQuestion it answers
PORTWhich door (and which transport protocol)?
STATEIs it open, closed, or filtered by a firewall?
SERVICEWhat kind of software usually lives there?
VERSIONWhich product and release is answering?

open = something accepted the connection · closed = reachable but nothing listening · filtered = a device is blocking the probe, so the state is unknown.

Fast Port Discovery

A fast scan checks the 100 most common TCP ports. It is a quick, shallow look — perfect for a first pass, never a complete picture. You will run it from the Kali Linux VM against the IP address of your Metasploitable 2 VM.

TARGET DOSSIER

What is Metasploitable 2?

The machine you are authorised to scan in this lab — and the reason this workshop is safe to practise in.

INTENTIONALLY VULNERABLE · TRAINING ONLY
What it is

A deliberately vulnerable Linux virtual machine built by Rapid7 as a training target. It ships with a whole set of outdated, default-configured and misconfigured services — FTP, Telnet, SSH, SMTP, DNS, HTTP, SMB and databases — so that learners always have realistic, findable evidence to work with instead of a toy example. In this lab it is the victim: victim-ip.

How it helps you learn ethical hacking
  • A safe, legal place to practise. You can scan, enumerate and repeat as many times as you like without touching a production system — and without ever needing permission from a stranger.
  • Classic services behave realistically. What you see here mirrors what you will meet in real assessments: legacy protocols, verbose banners, weak defaults.
  • Facts connect to real-world knowledge. Findings map to documented CVEs, so you learn to research a version instead of memorising a trick.
  • It teaches method, not heroics. The skills you build — discover, enumerate, interpret, verify — transfer to any network you are authorised to test.
⚠ How to treat it safely
  • Keep it on an isolated lab network (host-only or NAT adapter). Never connect it to the internet or a corporate LAN.
  • Take a VM snapshot before you start, so you can reset the image at any time.
  • Scan only this VM from your Kali VM. The authorization covers this training target and nothing else.
nmap -F victim-ip

💡 Guiding questions for your three choices

  • Does this service need to be reachable from this network at all?
  • Does it use cleartext credentials or data?
  • Would it be valuable to an attacker if misconfigured (file access, database, remote shell)?
  • Is its version old enough that you should look up its history?
  • Can you get more information about it safely with another scan?

Remember the framing

An open port is an observation, not a finding. & "This is a good target" is the wrong sentence. The right sentence is: "This service offers the most information to validate next, and here is what I would check."

Nmap Scripting Engine

NSE = Nmap Scripting Engine. It lets Nmap do far more than knock on doors: scripts can grab extra information, test configurations, and check for signs of known issues — all using Nmap's own engine.

How it works, in one sentence

An NSE script is a small program with rules about when it runs. Nmap decides which hosts and ports qualify, runs the script there, and prints its findings with the scan results.

Target foundhost & port
⟶
Rule matchesscript eligible
⟶
Script runssends its probes
⟶
Output printedfacts + leads

Script categories at a glance

discovery

Finds more about hosts and services than a plain scan would.

safe

Designed not to crash or disrupt the target. Still real traffic.

default

The set Nmap runs when you use -sC. A balanced starting point.

version

Helps refine version detection.

vuln

Checks for signs of known issues. Can produce false positives — verify everything.

auth

Examines authentication behaviour and configuration.

brute

Password guessing. Not used here. It is disruptive and out of scope for this workshop.

Enumeration ≠ Exploitation — know the line

Enumeration gathers information; exploitation uses it. This workshop walks both sides, but only ever against the Metasploitable 2 training VM in your isolated lab. On any other system, exploitation requires explicit written authorisation, a defined scope and a rollback plan — and unauthorised access is a criminal offence, not a lab exercise. The professional habit to build here is: hold the boundary, and get permission in writing before you cross it.

⚠ Script Safety

  • Read first, run second. Know what a script does before you run it — especially vuln, intrusive and brute scripts.
  • Timeouts and load matter. Some scripts send many probes and can disturb a fragile service.
  • Outside an isolated lab, ask for permission in writing. A "harmless" script can still trigger alerts or outages.
  • Stay on target. Here, that is victim-ip only.
nmap --script vuln victim-ip

Runs every script in the vuln category against the target. Expect noisy, partial, sometimes inconclusive results — that is exactly what a real analyst has to triage.

attacker@kali: ~/lab — nse vuln category

Targeted, gentle example

nmap --script ftp-anon -p 21 victim-ip
--script ftp-anon

Run one named script: does this FTP service allow anonymous login?

-p 21

Limit the scan to port 21 only — less traffic, less noise, faster answers.

attacker@kali: ~/lab — ftp-anon

Why this is a good teaching example: the script answers one narrow question, produces a clear yes/no, and its result is directly useful for a configuration decision.

✗ A human must verify

YOU OWN THIS
  • Whether the service actually exists — on this host, right now.
  • Whether the version is accurate — banners can be wrong, patched or faked.
  • Whether a vulnerability applies — the product, the release, the feature, the configuration.
  • Whether the finding is exploitable — reachable, enabled, and not blocked by controls.
  • Business impact — what this system actually does and holds.
  • False positives — and, just as important, false negatives the AI never mentioned.
  • Remediation decisions — what to change, when, and who approves it.

Golden rules of AI-assisted analysis

  1. Verify the version with a second, independent check.
  2. Confirm applicability — does this product, release and feature combination match?
  3. Gather evidence — commands, output, timestamps. No evidence, no finding.
  4. State your confidence — confirmed, likely, or unverified.
  5. Never paste sensitive data into an external AI service unless policy allows it.
  6. Treat AI text as a draft, not a source of truth.
